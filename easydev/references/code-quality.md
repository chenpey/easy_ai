# 代码质量判据

写代码与审查可维护性时的唯一细则源，与全局规则 `AGENTS.md` §5 保持同步；其他模块链接本文件，不另抄细则。先满足需求、正确性与安全，再谈写法。本文件不改变风险分流、验证要求与审查强度。

## 克制复杂度与边界校验

只在系统边界（用户输入、外部 API、文件 IO）校验与处理错误，不对不可能发生的情况做防御性处理；外部数据只在入口校验一次（不可信结构化输入用 schema 校验库解析），内部直接信任已校验类型。仅在有具体触发路径时说明失败方式与成本再加防御；涉及授权、资金、数据丢失、敏感信息的边界不适用“几乎不会发生”的豁免。
- 正例：`const cfg = ConfigSchema.parse(raw)` 在入口解析一次，后续直接使用 `cfg`。
- 反例：手写零散字段检查，或在三个内部函数里把同一个端口值各查一遍。

## 结构与抽象

默认写直线式代码：只被调用一次的逻辑与变量一律内联，不拆辅助函数；仅当同一逻辑有 2 处以上真实复用时才提取。不加未被要求的类、接口、配置项、参数、wrapper；除非明确要求，不写备份、回退、降级、兼容旧版本逻辑。代码尽量短，能一个表达式清楚表达的不拆成多步，但不写嵌套三元与链式黑魔法；犹豫要不要抽象或加保护时选更简单的。
- 正例：`submitOrder()` 直线写清正常流程，两处复用的规则才提成函数。
- 反例：每两行包一个只调用一次的 `helper1()`，或提前加未要求的兼容分支。

## 控制流

提前返回，少用 else；能用不可变绑定就不用可变变量；用三元或提前返回代替重新赋值。
- 正例：`if (!item) return null;` 之后继续写正常流程。
- 反例：三层 `if/else` 里用 `let result` 反复重新赋值。

## 类型与异常

不用逃生舱写法（`any`、无理由的类型断言、吞掉异常的空 catch）；能靠类型推断就不写冗余标注。仅在当前层有明确处理职责（恢复、错误转换、补充上下文）时使用 `try/catch`，否则让异常向负责处理的边界传播。不得为简化代码删减必要的错误处理或资源清理，尤其是防数据丢失的处理。
- 正例：仓储层把驱动异常转成 `OrderNotFound`，保留原始 cause。
- 反例：`catch {}` 吞掉写入失败，调用方以为已落库。

## 同步与异步

同步逻辑保持同步；只有真正涉及异步或副作用的函数才返回异步结果。
- 正例：`formatTotal()` 返回数值，`saveOrder()` 才返回 Promise。
- 反例：纯计算函数也声明 `async`，调用方被迫 `await`。

## 依赖方向

遵守既有分层与依赖方向，不引入反向或循环依赖；跨模块归属沿用已有职责划分。
- 正例：领域层不 import 基础设施层，由调用方注入。
- 反例：`domain/order.ts` import `db/pool.ts`，形成反向依赖。

## 术语

沿用仓库已定义的术语与命名，不自造同义词；仓库明确区分的概念不混用。
- 正例：全仓沿用既有的 `Order` 类型与「订单」表述。
- 反例：同一概念在不同文件里叫 `order`、`purchase`、`deal`。

## 注释

只写代码本身表达不了的原因、约束、单位与取舍；关键安全条件与不可见约束必须写明。行为变化时同步更新，保留有效的已有注释。不用固定注释前缀，也不用 `TODO` 掩盖验收缺口。
- 正例：`// 金额以分为单位，避免浮点误差`
- 反例：`// 计数加一` 复述 `count++`，或把过期注释留在改过的逻辑上。

## 生成文件

不手改生成产物；改源头后重新生成，并把生成结果与源头改动一并纳入变更集。
- 正例：改 `schema.graphql` 后运行生成命令，两侧改动一起提交。
- 反例：直接编辑 `generated/api.ts`，下次生成即被覆盖。
