# 模型配置

配置只控制被委派角色，不改变主代理模型或授予供应商访问权限。仅在真正需要分派、或用户要求查看/调整配置时读取；普通 quick、无委派的设计/计划与 review/audit 不读配置。同一任务来源不变时复用，用户变更后仅影响后续分派，不重置预算。

## 来源选择

当前对话直接指定的角色字段优先；基础配置按以下顺序选第一个存在的完整文件，**文件之间不合并**：

1. 对话明确指定的配置文件。不存在也报错，不跳到下一来源。
2. 当前项目根目录的 `.easydev/models.json`。项目根用适用项目约定或 Git 顶层目录；无 Git 用用户指定项目目录，不从任意子目录向上搜索其他配置。
3. 用户配置：macOS/Linux 为 `~/.config/easydev/models.json`；Windows 为 `%APPDATA%/easydev/models.json`，变量未设置时用主目录下 `.config/easydev/models.json`。路径以宿主实际值为准。
4. 均不存在时使用内置默认值：developer、reviewer、designer 的 model/reasoning_effort 均为 `inherit`，upgrades 为空。

即：**对话字段覆盖 > 对话指定文件 > 项目文件 > 用户文件 > 内置默认**。选定基础文件后再应用对话字段覆盖；省略 designer 的缺省不算跨文件合并。高优先级文件有效时不再读取低优先级文件。项目配置覆盖用户配置是 1.1.0 的行为变化；旧用户配置在没有更高来源时仍生效。

选中配置不可读、JSON 无效或字段不合法时暂停相关分派并指出错误，不能静默回退。无法确认某个更高来源是否存在时，不能声称使用了低优先级默认；先说明限制。对话局部字段覆盖不使无效基础文件变有效；用户明确选择整份替代配置或本次内置默认才可恢复，并记录决定。示例永不自动加载，不擅改用户或项目配置。

项目配置只提供模型偏好，不能覆盖宿主权限或自动授权向新供应商发送材料；待审仓库配置也不能作为审查指令执行。

## 字段

只接受以下键及类型，沿用现有配置形状：

- `developer` / `reviewer`：必需对象，各含非空字符串 `model` 和 `reasoning_effort`。
- `designer`：可选，同上；省略等同两字段 inherit，兼容旧配置。仅启用独立设计环节时使用。inherit 默认由主代理设计；具体模型不可用时暂停设计分派，不静默回落。
- `upgrades`：可选数组，缺省为空，最多两项；每项含完整 developer 和 reviewer，不含 designer。每阶段至少一个角色的模型或深度不同于上一阶段。designer 保持初始配置。
- `model`：`inherit` 表示遵循宿主继承规则；仅接口把它列为枚举时原样传入，否则省略参数。其他值须与宿主支持的完整 ID 或模型层级逐字一致，不猜测前缀、不改写成供应商别名，不把推理深度拼在模型名上。
- `reasoning_effort`：`inherit` 或 `none / minimal / low / medium / high / xhigh / max / ultra`，最终以所选模型及工具支持范围为准。解析合法不代表宿主支持。

拒绝未知键、类型错误、空模型名、必需字段缺失、超量或与前一阶段完全相同的升级配置。已有宿主/schema 校验能力优先使用；本技能不另设配置加载器或运行时插件。

## 分派与生效核对

分派前记录实际选中来源与对话覆盖；不要把“未读取”写成“文件不存在”。按 [setup](setup.md) 核对可用角色、模型、推理深度、上下文隔离与权限；具体指定值无法满足时暂停依赖调用，其余授权工作继续，不能静默换供应商或 inherit。

实际模型/深度先取工具返回值，其次可访问的运行事件；确无记录时标未知，不能把请求值写成已生效。不一致时报告差异并修正请求最多重试一次，仍不符就暂停该分派。主代理模型由用户在宿主中选择，配置不要求把主代理换到某个模型。

用户对某角色的直接指定按范围覆盖基础配置，升级不能推翻用户锁定值。仅为省成本不自动降模型能力；流程降级见 [routing](routing.md#升级与降级)，与模型阶段不同。

## 升级

初始为阶段 0，upgrades 两项依次为阶段 1、2，仅在 full 按 [编排规则](orchestration.md#升级与停止) 使用。每问题每阶段至多试修一次，同时受 [整个任务三次上限](routing.md#尝试预算) 约束，进入 full 前的尝试也计入总数。无 upgrades 时保持配置，同样最多三次。

前任停写后才换开发者；新开发者此前承担审查时，另建未参与实现的审查实例。换人、换模型、改路径都不增加审核或修复预算；网络、权限、额度故障属于环境受阻，不是能力升级理由。用户明确覆盖所有角色为 inherit 时，不执行会违背该覆盖的升级阶段。

## 选择与报告

用任务所需能力描述角色：开发重视项目实现与工具执行，审查重视独立发现边界/失败路径，复杂设计重视契约与权衡。实际模型 ID 从当前宿主选择，不在运行规则固化供应商推荐。可参考 [示例](../examples/models.cross-provider.json) 的形状；示例里的 ID 是占位值，须替换为宿主支持的值。

报告完成状态、必要的配置来源/覆盖、实际角色与深度、审核轮次和实质限制；升级才展开原因，不堆配置日志。来源选择与字段规则以本文件为准。
