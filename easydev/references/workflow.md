# 流程编排

主代理独占流程状态：分流、分派、预算与宣布完成。子代理只回报新证据。

## 分流判定

先确认交付类型：仅要 design/plan/debug/review/audit/spike 时只交对应产物，不自动扩大为实现。用户指定的档位、范围与授权优先，但指定档位低于任务触及的高风险边界所需时（如指定 quick/normal 改动鉴权、支付、数据破坏等），不得静默降档；交互环境下先暂停披露高风险边界与缺失独立审查风险，取得明确放宽确认后方可降档并在交付中断言未覆盖风险；非交互或未获放宽确认时按风险所需档位（full）执行并报告偏离。

读目标、直接调用方、相关测试及实际发布/数据边界后，对相关风险区分三态：

- **已排除**：有能推翻风险假设的证据，例如调用方一起发布、接口输入输出不变、不改变鉴权决策。搜索无命中不能排除动态调用或外部客户端。
- **已确认涉及**：指出受影响入口、不变量和具体失败方式。
- **尚未核实**：有具体线索但决定风险的条件仍不明；继续最小调查，仍不明则进入 full。不把“还没看”写成“已排除”，也不穷尽无依据的假想风险。

**第二视角信号**，命中任一即具备：

1. 改动行为没有现成检查能拦截回归。「现成」指改动前已存在且仍有效，作者本次新增的测试不算；纯新增行为、纯展示文案与注释不因此命中，但期望值仍须追溯到需求或独立契约。
2. 同一改动被两个及以上独立调用方或消费方依赖。
3. 改动共享契约（接口、配置格式或数据语义），且存在本次未改动的使用方。
4. 用户明确要求独立审查。

| 路径 | 条件 | 完成方式 |
| --- | --- | --- |
| quick | 目标明确、局部低风险、无第二视角信号；兼容的内部机械重命名也适用 | 入口核心：实施、验证、自查 |
| normal | 影响有界，具第二视角信号，无 full 条件 | 一次独立定向审查，至多一次局部 P2 修复与复审 |
| full | 触及下方高风险边界；重大外部契约或持久数据影响（破坏兼容、独立发布客户端需迁移、改变存量数据语义、难以回滚）；有线索的关键不确定性经调查仍不明；或用户要求完整闭环 | 按 [full 编排](#full-编排)；命中 [设计门控](design.md#启用门控) 才启用独立设计 |

文件数、调用方数量或单纯提到 API 不定档；有证据的兼容增量可为 normal。先分流，再判设计门控，不能用门控反向把 quick/normal 升级。

## 高风险边界

以下是典型触发条件，不是关键词清单：

| 边界 | 需要核对的实际影响 |
| --- | --- |
| 安全、鉴权与授权 | 信任边界、身份/对象/租户权限、注入与隔离 |
| 支付、敏感数据 | 资金与账务不变量、凭证和个人数据的访问/存储/传输 |
| 并发与数据操作 | 重复执行、一致性、破坏性写入、迁移兼容及失败恢复 |
| 密码学与随机数 | 加密/签名/密钥管理、安全令牌的随机性；普通展示随机数不算 |
| CI、构建、IaC、权限配置 | 凭证暴露、发布/部署权限、制品可信性、基础设施破坏 |
| 依赖与供应链 | 来源/完整性、生命周期脚本、执行权限、生产关键依赖的行为或兼容变化 |
| 生产日志与遥测 | 密钥、令牌、个人数据是否被记录、外发或扩大可见范围 |

上表按实际影响判定：只改注释、展示文案、错误提示措辞或不含敏感字段的日志措辞、未改变该行所列影响的，不因此进入 full；因其他理由已在 full 的照常执行。

## normal 流程

1. 在上下文记录目标、基线（含敏感基线路径）、影响依据、同一问题尝试数与已用审查次数；默认不建 full 账本；长任务或需跨会话恢复时保存最小记录。
2. 实施保持单写入者，允许只读并行；验证沿用 quick 核心；实现改动（非纯文案与注释）按 [代码质量判据](engineering.md#代码质量判据)。
3. 开工先按 [模型配置](environment.md#模型配置) 核实角色模型。不同实例按 [审查角色](roles.md#审查角色) 审完整任务 diff、直接调用方、相关测试与验收；交接给原始要求与证据路径，单独一行写 `角色：reviewer`，并给出 roles.md 审查角色小节路径与 `**[P级] 简短标题**` 起头格式。diff 跨独立片时可按 [并行执行](#并行执行) 分派。
4. 首轮无必关项、验收满足且证据对应最终版本即交付，注明“一次独立定向审查”，不称 full 闭环；不影响验收的 P3 列为未实施建议。
5. 首轮仅报局部 P2 时，允许一次局部修复加一次定向复审；normal 内独立审查硬上限 2 次。发起前核对历史预算，尝试已满或无复审轮次时停止，不做无复审机会的修复。
6. 出现 P0/P1、非局部 P2、验收缺口、有线索未排除的潜在 P0/P1，或复审仍未关闭时转 full，继承发现、尝试、已用审查与候选评审（转 full 后记入 `d/3`）：首轮后转 full 记 `r=1/5`，复审后转 full 记 `r=2/5`；此前用过 full 的在原轮次上累加。

**局部 P2 判定**（逐条对照，确认确属局部 P2，不看缺陷措辞）：① 不触公共契约：对外 API、CLI 参数与输出、配置格式、事件 schema 均不变；② 不改数据或状态语义；③ 不引入新依赖，不越出本任务已改文件与其直接调用方；④ 不是验收缺口，也没有有线索未排除的潜在 P0/P1；⑤ 任一条无法用 diff、调用方清单或检查结果确证时按非局部处理，转 full。

审查后再有实质修改，原审查不能证明最终版本；除上述一次局部修复外一律转 full 复核，纯报告排版不计。没有独立能力时按 [能力降级](environment.md#宿主适配与能力降级) 处理，自查不算独立审查。

## full 编排

流程：明确验收与基线 → 开发与验证 → 冻结修改 → 独立审查 → 核实发现 → 有限修复与复审 → 交付。

- **角色**：开工先按 [模型配置](environment.md#模型配置) 核实角色模型与深度。审查者须与设计者、实现者为不同实例，设计者可兼任实现者。主代理可作唯一开发写入者、只委派审查者，前提是处于模型阶段 0 且 `developer` 的模型与深度均为 `inherit`；此时审查仍须由独立实例承担，报告标「实现=主代理」，不因主代理写入降级为自查。用户明确授权主代理自查（含明确禁止委派；无委派能力时先按 [能力降级](environment.md#能力降级与审查包) 暂停并经用户确认）时才标「自查（非独立）」并交付审查包；否则委派开发者。交付验收阶段不等于模型升级阶段。上下文明显膨胀或具备合规并行条件时也可委派实现片，报告原因。
- **写入者**：同一写集同一时刻只有一个写入者；换开发者须前任停写，预算不重置。并行规则见 [并行执行](#并行执行)。
- **审查时机**：命中设计门控时施工前审冻结的 `design.md`（见 [施工闸](design.md#收敛与施工闸)）；普通实施在完成相关改动与验证后对完整任务变更初审，有修复时定向复审；高风险公共契约将被后续阶段依赖时，在依赖形成前先做阶段增量审查；修复改变契约或影响范围时沿受影响路径扩展复审。审查强度按 [强度分档](review.md#强度分档)，高风险边界最低「深」。

## 并行执行

按内容判断并行，不以串并行对照评测作为启用前置。内容自判 1–5 片，用户指定片数优先；1 片即串行，默认不追求用满。同批活跃代理片（含提前审查）合计最多 5 片，不嵌套倍增。用户指定须为整数 1–5；指定 0、6 等越界或非整数时不启动该批分派，说明范围并等待改值。合法指定仍受安全门槛、独立片数与宿主额度限制；不能满足时报告冲突并采用可行的较少片数或串行，不为凑数拆片。判不准、无并行能力或被限流时串行，不算降级。

并行写入仅限 full；normal 保持单写。独立性与隔离条件全部成立才可并行，否则串行。**独立片**须同时满足：每片唯一写入者，写集互不相交；不依赖其他片尚未完成的结果；共享契约已冻结，各片可独立验证；单片工作量须大于调度开销。交接列写集、读取及验证依赖、工作区和资源，并简记判断依据；任一写集会改变其他片验证前提时串行。锁文件、生成物、迁移序号、公共配置等共享写点由主代理协调当前获授权写入者在拆分前或集成时串行处理；无法拆开依赖则冲突组串行。

高风险边界默认串行（鉴权、支付、敏感数据、迁移、发布权限等）；仅用户明确要求该高风险工作并行、上述独立性与下述隔离条件全部满足且每片可独立验证和恢复时例外。指定片数不等于高风险并行授权。账本记录高风险并行理由、用户授权来源、风险、隔离与恢复方式；不放宽 full、设计门控、独立审查或操作授权。

1. **只读并行**：调查、分片审查与证据核对无依赖且工作量大于调度开销时，按内容或用户指定取 1–5 片；同一冻结快照合计一轮。normal 可分派多个审查实例，主代理核对合并覆盖完整任务 diff 与调用链，仍计一次。
2. **审查流水线**（full）：片及其验证依赖冻结、验证后可提前送审，占 `r`；其他写入者仅继续不影响该快照的工作。写集、调用方、共享契约或验证依赖变化使相关证据失效，重审另占轮次。增量余量耗尽时停止可选流水线，收齐改动后终审；必须先审的高风险契约未通过时不得施工其下游，余量不足则报未完成。
3. **隔离与验证**：需运行构建或测试的并行写入须用独立工作树，按 [工作区隔离](environment.md#工作区隔离与分支收尾) 核对同一任务基线（含已保护的相关未提交及未跟踪改动）并返回分片改动；端口、数据库、测试数据与输出目录须隔离。仅纯文档或可证明无构建、验证干扰时共享工作区；无法隔离则串行。主代理协调各批验证及最终整仓验证期间所有相关写入者停写，收齐停写确认后验证；验证失败或未验证片不得作为完成片集成。分片验证不替代最终完整检查；完成集成与完整检查后冻结完整任务 diff 终审。
4. **集成与预算**：主代理指定单一集成者，逐片相对交接基线核对 diff（含新增、删除与未跟踪），不拾取用户或其他片改动，不操作共享 Git 索引；越界先停片调查，不自动覆盖或撤销。初次集成失败先取证；提交有新证据的候选修复才占一次尝试，返工同样适用。同根因跨片共用问题预算，不因换片、换写入者重置；复验不重复计次。独立片可继续，涉及共享契约或污染验证时先停相关片；模型升级先暂停本任务全部并行写入，沿 [升级与停止](#升级与停止) 串行交接。full 账本记录片、写入者、状态与任务共用 `r/5`、`d/3`。
5. **真实证据**：记录实际并发证据（分派事件或开始/结束时间区间，须证明执行重叠），以及判断依据 + 风险与隔离方式。串行包装不得称并行；计划同时分派或多个角色不等于实际并发。没有真实重叠时如实报告串行；未做收益测量不得宣称提速。

## 审查预算

| 账 | 上限 | 计入 |
| --- | --- | --- |
| 设计审查 `d/3` | 3 轮 | 设计审查、候选评审、升版重审 |
| 施工审核 `r/5` | 5 轮 | 阶段增量审查、完整初审、复审 |

两本账互不占用、互不退还；上限不是目标。每次发起独立审查即占一轮，完成或受阻后更新状态；工具重连同一次未完审查不另计，连续重连超过 2 次按环境受阻报告。终审前须为最终完整审查与复审预留两轮，因此阶段增量审查轮数 = max(0, min(3, 5 - 已用轮数 - 2))，已有 normal 等审查也占余额，需预检的契约更多时按依赖合批。原审查失效不退轮次；可选流水线收敛见上节，强制前置审查不得延到终审。轮次不因改称、换实例、换问题号或降级而重置。

## 账本与交接

小任务记在上下文；长任务或需恢复时在 [任务目录](environment.md#任务目录与恢复) 保存 `ledger.md`，交接给绝对路径：

```text
目标/验收/范围/授权基线（可直接执行、需确认、禁止）：
基线提交/用户已有改动/原内容位置：
阶段/写入者（并行时列片、写集与状态）/配置来源/实际模型与深度：
设计环节（门控命中项或不启用理由）/design.md 版本与冻结时间/设计者：
审查强度/d/3 与 r/5（占用、完成或受阻）：
并行判断（自判或用户指定片数/实际片数/判断依据 + 风险与隔离方式/宿主额度/授权来源/实际并发证据路径）：
问题 ID/证据状态/累计尝试/验证结果/关闭依据：
验证命令/退出状态/对应版本：
未覆盖/阻塞/下一步：
```

交接以摘要加可回查路径传递：单独一行写 `角色：developer`、`角色：reviewer` 或 `角色：designer`，并给出 [roles.md](roles.md) 对应小节路径；附原始目标与验收、关键契约、基线与当前版本、已完成事项与证据路径、未解决问题与剩余预算；设计环节补 `design.md` 路径、冻结版本与 `d/3`；并行片补写集与写集外禁写。审查者可访问完整任务 diff 与必要调用链；定向复审补上次审查版本、修复 diff 与问题编号。开发者解释是待核实材料。子代理不直接向用户提问，由主代理合并真正需要用户决定的事项。交接里的 `角色：x` 是流程标识，宿主 agent 名按可用角色清单映射（如 `worker`/`reviewer`/`oracle`），不把 `developer`/`designer` 直接当宿主 agent 名。

## 审查与修复

1. 送审前主代理按基线核对完整变更（含新增、删除、重命名、未跟踪），确认证据对应当前版本；归属不明先调查，不自动撤销。
2. 新审查实例同轮核对需求验收、实现质量与调用链，按 [审查规程](review.md) 输出；待审代码执行遵守 [不可信代码执行](review.md#不可信代码执行)。
3. 主代理核实每条发现：确认、排除或转待验证风险并入账。**P0/P1 的排除、降级或转风险须由审查者核对证据**，无复核不得关闭。主代理兼作者时，排除、降级或移出发现须附代码、调用路径、可复现检查或需求原文：可复现的交同轮审查者复核，否则交下一轮独立确认，确认前标“作者有争议、未关闭”。设计层实质改动须升版并计入 `d`。
4. 写入者（主代理或委派开发者）按 [处理审查反馈](engineering.md#处理审查反馈) 修复并补证据；复审从原问题、修复 diff 与测试开始，拟通过时通览完整任务 diff。同一审查者可复审；审查者不修自己要审的版本。

| 发现 | 处置 | 末轮仍未关闭 |
| --- | --- | --- |
| 确认 P0/P1、范围内 P2 | 必须关闭并补验证，触发复审 | 停止自动修复，报**未完成** |
| 验收缺口（含标为 P3 者） | 必须修复，不靠降级标签绕过 | 报**未完成**或**部分完成/待确认** |
| 不影响验收的 P3 | 记位置与代价，作未实施建议 | 正常交付并列出 |
| 待验证风险 | 列线索、成立条件、影响与最小确认法 | 含潜在 P0/P1 时报**部分完成/待确认** |
| 作者争议 | 附证据，按第 3 条复核 | 交用户，标**作者有争议、未关闭** |
| 历史债、越界、用户接受的缺陷 | 不扩任务，保留记录 | 按实际验收缺口标状态 |

## 升级与停止

- 先分阻塞类型：缺材料补上下文、假设错重新取证、边界不当调整拆分，均不占修复机会。
- 模型阶段为任务级状态（升级后全任务沿用）。配有 `upgrades` 时，同一确认问题在每个模型阶段至多试修一次，失败或关闭证据不足时按序升入下一阶段（不回退、不重复同方案）；末级阶段可用尽剩余尝试，仍败即停，不回退弱模型、不自动补模型。送审用对应阶段的 `reviewer`；新开发模型曾任审查者时重建审查实例。
- 模型升级先暂停本任务并行写入，前任停写后交接现场（含未提交改动与失败证据），升级委派期间主代理不写入。默认原工作区串行；使用独立工作树须有 Git、已保护并核对任务基线，按 [工作区隔离](environment.md#工作区隔离与分支收尾) 交接。主代理协调在原工作区重验：不算新尝试，失败即该次尝试失败并停止自动修复。
- 升级不加审查轮数；末轮仍有待修缺陷时报未完成，不做无复审机会的修复。需扩范围、缺关键外部信息、终级无进展或预算到顶时停止自动循环，用户可显式扩预算并沿用原账本。
- 单次 review/audit 转授权修复时按分流重选路径；原只读审查只作修复前证据，不占正式轮次，修复后根因在设计且命中门控的记 `d=1`，其余记 `r=1`。normal 转 full 按 [normal 流程](#normal-流程) 继承。
- 模型不可用、权限或网络失败是环境受阻，不耗修复次数、不构成升级理由；报告受阻阶段并继续不依赖它的授权工作。
- 无待修缺陷时按 [完成边界](engineering.md#完成边界) 立即交付，不凑轮数。

## 路径升降级

风险或实际影响扩大时携证据升级；单次失败、跨文件或多一次工具调用不是升级理由，仅为刷新预算切路径无效。

降级（full→normal/quick、normal→quick）须同时满足：新证据推翻原触发条件且目标路径条件全部成立；用户没有指定原档位；没有未关闭必关项、高影响待验证风险或作者争议。例外：用户在初始分流时明确指定低档位、且已按 [分流判定](#分流判定) 经充分风险披露后明确确认接受未覆盖风险的，按用户接受的风险档位执行（记录为用户风险接受，不视为技术反证成立的路径降级，报告中必须断言未覆盖风险）。降级只减少尚未发生的流程：已有设计、发现、尝试与审查轮次保留；重入 full 不退还 `d/3`、`r/5`，降级回 normal 也不重新获得已用的 normal 审查。

**能力降级不等于流程降级**：缺少子代理不会让支付、鉴权等任务变成低风险；保留原风险判断，说明缺少的保障。

## 尝试预算

同一问题在整个任务最多三次有新证据的候选修复尝试，quick、normal、full、换实例与模型阶段共用；三次仍失败或证据不足即停止自动修复，报告目标不变量、已暴露的耦合位置、最小修复是否成立与剩余缺口，不因失败次数推断必须重写架构。一次尝试从提交候选修复开始，下一次须有新证据；纯调查与环境故障不计次，但不清除已有记录。问题身份按根因或症状识别，换编号不获得新预算。

## 报告

说明完成状态、改动与验证、实际模型与深度（不可得写未知）、独立审查次数与 `d/3`、`r/5` 使用、确认问题与关闭状态、实质限制；启用设计环节或候选评审时按 [设计报告](design.md#报告) 补充。模型与深度以工具返回值或运行记录为准，不把请求值当实际值。只在升级、角色互换或模型适配时解释原因；账本供恢复，不向用户堆过程日志。
