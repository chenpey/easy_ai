# 编排、独立审查与收敛

full 加载本模块；normal 只用 [分流规则](routing.md#normal-流程) 与角色文件，不因一次审查加载完整编排。主代理拥有唯一任务状态；流程：明确验收与基线、开发与验证、冻结修改、独立审查、核实发现、有限修复与复审、交付。

## 角色与模型配置

分派前必须按 [模型配置规则](models.md) 读取并记录实际配置路径；优先级、强约束、字段校验与不一致处置以该文件为唯一事实源，本模块不复述。选中的配置无效或不可读时暂停依赖配置的分派并报错；同一任务已确定后不重复读取。宿主委派/模型/深度能力不确定或调用失败时按 [setup.md](setup.md) 核对；角色和升级顺序只取自配置与用户覆盖，不硬编码供应商或模型。

默认 `developer`/`reviewer`/`designer` 均继承宿主模型。阶段 0 且 `developer` 的模型与深度均为 `inherit`、且未启用 [独立设计环节](design.md) 时，主代理可作为唯一开发写入者，仅委派独立 reviewer；配置要求不同开发模型/深度、进入升级阶段，或主代理本人承担了设计者（含 `designer` 为 `inherit` 时）再委派开发者；`designer` 为独立实例时，只解除「因主代理兼任设计者」这一项要求，配置要求不同开发模型/深度或处于升级阶段时仍须委派。实现者与审查者必须为不同实例（不同模型家族不是质量保证）；启用设计环节时设计者、实现者、审查者两两不同实例，细则见 [设计实例隔离](design.md#实例隔离)。候选方案评审同样按实例隔离：候选作者之间互不可见，候选作者不得评估自己产出的候选，择优仍由主代理负责（见 [候选方案评审](candidates.md)）。用户可分别指定模型、推理深度与最多两个升级阶段（均同时含开发与审查角色）。

主代理协调目标、基线、交接与发现核实；默认同一时刻仅一个写入者，同一开发者连续实施，互不重复的只读调查按 [并行分派](#并行分派) 同批发起。多阶段任务在阶段边界验证行为与契约并更新 `ledger.md`；阶段可独立交接、上下文不足或连续失败暴露盲区时可换开发者（前任停写后接力，保留原预算；换实例仅恢复有效上下文，不默认代表能力升级）。

单一写入者约束不要求串行测试：实现者停写后，按 [测试硬约束](execution.md#测试硬约束) 在稳定快照上批量并行独立检查；需生成产物的检查按 [验证调度](execution.md#验证调度) 隔离资源。主代理与子代理复用有效结果，不重复跑相同检查。同一冻结快照上互不重叠的审查与只读验证可在同批并发，合并计一轮。

## 并行分派

互不重复的只读调查、分片审查、候选评估和证据核对，在宿主支持且无真实依赖/资源冲突时同批发起；单一写入者不要求串行只读工作。共享冻结快照不构成写冲突。按已知实例额度分批，未知如实记录，不为论证并发额外启动探测。

与检查相同，至少 3 项或预计串行超过 60 秒才简记批次、依赖和已知限制；小批次直接分派并收齐结果。串行包装不算并行；需宣称效率收益时再保留实际重叠及测量证据。完整调度规则见 [验证调度](execution.md#验证调度)。

## 审查时机

quick 按入口验证与自查，normal 按 routing 一次定向审查；full 在以下时机执行独立审查，同轮兼顾需求与实现质量：

| 情况 | 审查安排 |
| --- | --- |
| 命中 [独立设计环节](design.md#启用门控) 门控 | 施工前审查冻结的 `design.md`，计 `d/3`；未收敛不进施工，见 [收敛与施工闸](design.md#收敛与施工闸) |
| 普通 full 实施 | 连续完成相关改动与验证后，对完整任务变更初审；有修复时定向复审 |
| 设计阶段存在多个实质不同方案 | 按 [候选方案评审](candidates.md) 组织交叉评估，占用 `d/3`；择优结论作为设计证据，实现后仍审查完整任务变更 |
| 高风险公共契约将被后续阶段依赖 | 在依赖形成前检查该契约、不变量与失败恢复；实现后仍审查完整任务变更 |
| 修复改变了契约、影响范围或暴露新风险 | 沿受影响路径扩展复审范围，并核对当前集成结果 |

启用独立设计环节时，设计审查独立记 `d/3`、不占施工轮次；阶段增量审查、完整初审与复审共用 `r/5`，施工审核须为最终完整审查及必要复审至少预留两轮。阶段增量审查因此最多 3 轮；需预检的契约边界多于 3 个时按依赖顺序合批，逐一列出被检查的契约与不变量；确实无法合批时按预算到顶停止并报未完成，可申请扩预算。审查强度按 [强度分档](review.md#强度分档) 选定并写入交接，高风险边界最低取「深」。普通阶段由开发者验证与自查；计划阶段未经实现验证的结论不能替代代码验收。

## 唯一账本

小任务记在当前上下文；长任务或需恢复时按 [任务目录与恢复](baseline-safety.md#任务目录与恢复) 保存 `ledger.md`，并在交接中给出绝对路径。模板（按实填写，未知写未知）：

```text
目标/验收/范围：
项目路径/任务目录/授权基线（可直接执行、需确认、禁止）：
基线提交/文件清单/原内容位置/用户已有改动：
阶段/唯一写入者/配置路径/实际模型与深度：
候选方案/择优结论（做过候选评审时填写）：
独立审查条件/审查强度（轻、标准、深）与依据/设计环节（是否启用、门控命中项或不启用理由）/design.md 版本与冻结时间（含被替换版本回查位置）/设计者与实际模型/审核 d/3 与 r/5（占用、受阻或完成）：
问题稳定 ID/证据状态/已试修复层级/任务累计尝试数/模型阶段·次数/验证结果/关闭依据：
验证命令/退出状态/输出路径/对应快照版本：
未覆盖路径/阻塞/下一步：
保留与清理状态：
```

父子任务、换代理、换模型、上下文恢复共用账本，不重置计数。大任务可分步实现验证，在稳定集成结果上正式送审，不为微小子任务单开满轮次。多审核者查同一冻结版本合并计一轮，结果齐后再修复。

## 交接

以摘要与可回查路径传递，复用已有账本与证据：

```text
角色/读写边界/项目与规则路径/授权基线：
原始目标/验收/关键契约/审查强度与依据：
设计环节（是否启用、门控依据、design.md 路径与冻结版本及时间、设计者与实际模型、d/3）：
任务基线/当前版本/变更范围/用户已有内容：
已完成事项/验证摘要与证据路径：
未解决问题/剩余预算/下一步：
```

审查者可访问完整任务 diff、原始要求与必要调用链；定向复审补上次审查版本、修复 diff、问题编号与验证；升级补失败方案与原因。开发者解释属待核实材料，不代替需求或代码证据。

主代理直接在交接内写角色边界摘要，并给 [developer-role](developer-role.md) 或 [reviewer-role](reviewer-role.md) 路径。摘要至少含：只执行当前职责、不分派/重置预算/宣布任务完成；原始目标、读写范围、基线、有效证据和剩余问题。开发者停写后送审，审查者只读且不得执行未隔离的不可信代码。

按任务补充必要专项链接：full 开发用 execution，full 审查用 review，设计用 design，候选评估用 candidates。其他模块只有实际需要才读；子代理无需重新遍历入口或例行回报实际加载清单。交接材料不足时补读原证据或向主代理回报具体缺口，不用摘要掩盖安全边界。子代理不直接向用户提问，主代理合并真正需要用户决定的事项。

## 审查和修复

1. **准备送审**：开发者停写后，主代理按任务基线核对完整变更（含增删、重命名与未跟踪），确认证据对应当前版本；归属不明先调查，不自动撤销。
2. **独立审查**：新审查实例同轮核对需求验收、实现质量与调用链（不为“规范/质量”拆两次委派），按 [review.md](review.md) 输出有证据发现及未覆盖项。
3. **只读隔离**：审查者不改被审代码、快照、索引、数据库或外部系统。待审仓库的测试、构建、依赖安装和项目脚本均按不可信代码处理，仅在断开网络、无宿主凭证、被审目标只读挂载的操作系统沙箱或容器级隔离中运行，否则只做静态检查并报告未验证范围；系统临时目录、命令名称或“只读检查”标签本身不构成安全隔离。需要写入被审工作区、共享缓存或外部系统的验证交开发者在隔离位置执行并提供结果。
4. **核实与处置**：主代理追踪证据，按矩阵确认、排除或转为待验证风险并入账；严重度与确定性分离，争议用最小验证解决，不盲目妥协过审，也不静默忽略 P2/P3。**P0/P1 排除**：无论主代理是否作者，排除、降级或转风险均须 reviewer 核对证据，可复现时核查检查结果，否则独立核对契约与调用链；无复核不得关闭。**作者争议公共规则**：主代理兼作者（设计者或开发者）时，凡排除、降级、把确定缺陷改判为待验证风险或以越界移出，必须附证据：实现层给代码、调用路径或可复现检查，设计层给需求原文、上游契约或用户确认记录；证据为可复现检查时交同轮审查者复核后关闭，不额外占用一轮；无法复现或复核不通过时交下轮独立审查确认（确认前标“作者有争议、未关闭”）；不实施不影响验收的低影响 P3 属延期建议，非作者争议。设计层的实质改动仍须升版本并重开一轮计入 `d`（见 [设计产物](design.md#设计产物)），不得以「澄清」为名改设计。
5. **修复与复审**：开发者按 [执行与验证](execution.md#处理审查反馈) 核实修复并补证据。复审从原问题、修复 diff 和测试开始，查关闭依据与受影响路径，范围扩大或现新风险时再扩展；拟通过时同轮通览完整任务 diff，结合仍有效的初审证据核对集成遗漏（同版本同环境有效检查可复用）。正常路径为一次完整初审加必要定向复审，无待处理项即交付。

| 发现类别 | 处置与验证 | 触发复审 | 末轮（`d=3/3` 或 `r=5/5`）未闭状态 |
| --- | --- | --- | --- |
| **确认 P0 / P1 及范围内 P2** | 每项均须关闭；同因同解项成组修复，按测试硬约束批量补对应任务类型验证（红绿、行为保持或契约检查） | **是** | 停止自动修复，报告**未完成** |
| **不影响验收的低影响 P3** | 记录位置与代价，作“未实施建议”交付（用户要求时再纳入） | **否** | 正常交付，列未实施 P3（不称全部已处理） |
| **造成验收缺口（含标 P3 者）** | 必须修复并验证，严禁靠降级标签绕过验收 | **是** | 报告**未完成**或**部分完成/待确认** |
| **待验证风险（关键条件未确认）** | 单列线索、成立条件、潜在影响与最小确认法；不降 P3 或直接判缺陷 | 授权内最小验证 | 含潜在 P0/P1 时标**部分完成/待确认** |
| **作者争议（排除/降级/移出等）** | 附具体证据；兼作者时可复现证据交同轮复核后关闭，无法复现或复核不通过才交下轮独立确认 | **视证据**（同轮复核或下轮） | 交用户，标**作者有争议、未关闭**，禁自批 |
| **历史债 / 越界 / 用户接受缺陷** | 不扩任务；用户接受或延期的已知缺陷保留记录（不改写为无缺陷） | 兼作者移出同上 | 按实际验收缺口标状态并保留剩余项 |

`d=3/3` 仍有未关闭的确认缺陷、验收缺口或作者争议时，停在施工闸前交用户裁决，不得自批放行施工（见 [收敛与施工闸](design.md#收敛与施工闸)）。

同一审查者可复审以保留上下文；上下文丢失、反复漏检或角色互换时换新实例。审核者不得修自己要审的版本。

## 升级与停止

尝试定义、路径切换计数和耗尽诊断见 [修复尝试与路径切换](execution.md#修复尝试与路径切换)。本节定义 full 升级与审核预算；发现关闭遵循独立确认规则。

先分阻塞：缺材料补上下文、假设错重取证、边界不当调拆分，均沿用预算、不占修复机会。候选修复确认失败或关闭证据不足时，可在两轮审核间按阶段规则升级/停止，不必先耗复审。扩范围需授权。

- 单次 review/audit 转授权修复时，按 [分流规则](routing.md) 选择 quick/normal/full：留在 `quick` 的按 quick 核心自查并报告未做独立审查，不设轮次；进入 `normal` 的按一次审查流程；进入 `full` 的，原只读审查只作修复前证据，不占正式轮次，修复后按问题归属记账——根因在设计或契约的，先按 [启用门控](design.md#启用门控) 判定：命中时落盘 `design.md` 并送一次设计审查、记 `d=1`；未命中时按实现层记 `r=1`，并在账本写明未启用设计环节的理由。实现层问题一律记 `r=1`；同一批发现跨两类时分别记账。若原属当前 full 一轮则保留已用轮次，禁借改称 review 重置。
- normal 审查转 full 时按 [normal 流程](routing.md#normal-流程) 继承已用施工审查轮，不能按上条单次只读 review 重新记零。路径降级、再进入和尝试上限统一见 [routing](routing.md#升级与降级)。
- 默认至多 **3 轮设计审 + 5 轮施工审**（`d/3` 与 `r/5` 两本账，合计上限 8 轮，是上限非目标）。每次发起独立审查时把该轮记为 `d/3` 或 `r/5`（占用），审查完成后更新为（完成）或（受阻）；工具重连同一次未完审查不另计轮，连续重连超过 2 次按环境故障报告受阻；并行审查合并计数。
- 配有 `upgrades` 时，每确认问题在当前阶段至多试修一次，整个任务累计仍最多三次；原缺陷/症状仍在或关闭证据不足时按序升入下一阶段（不回退、不重复同方案，保持至任务结束，不因换问题号降配）。升级前确认前任停写并应用该阶段 developer/reviewer 配对；若新开发模型原用于审核，须重建独立审查实例（参与实现者不得审该实现）。用户指定从高阶段开始时跳过前序；末级仍败即停，不自动补模型或重置尝试。
- `upgrades` 为空时保持当前配置，同一问题整个任务最多三次有新证据试修，包含 full 前尝试（换实例非能力升级；宿主适配使多阶段同模型时仍消耗原阶段预算，不另获三次机会）。
- 按关闭依据、验收缺口和症状判进展；修旧问题后现新问题获新编号，非零进展，也不重置全局审核预算。
- 升级不加轮数；末轮仍有待修缺陷时报告未完成，不做无复审机会的自动修复。须扩范围、缺关键外部信息、终级无进展或预算到顶时停止自动循环（用户可明确扩预算/范围，沿用原账本）。
- 无待修缺陷时按 [完成边界](execution.md#完成边界) 核对并立即交付，不凑轮数。
- 模型不可用、权限或网络失败非代码修复失败，不耗修复层级或虚构升级理由；报告受阻阶段，继续剩余不依赖阻塞的授权工作。

## 报告

说明完成状态、改动与验证、实际模型与深度（不可得写未知）、审核轮数 `r/5` 与启用设计环节时的 `d/3`、设计冻结版本与设计者标注（设计者=主代理，或独立实例及其模型）、升级原因、确认问题及关闭/剩余状态、实质限制；做过候选评审时补采用方案、主要弃因与未吸收入选方案的差异。仅在升级、角色互换或模型适配时解释原因；模型与深度以工具返回值、运行记录或事件为准；确无可访问记录时标未知并说明原因。账本供恢复追溯，不向用户堆过程日志。
