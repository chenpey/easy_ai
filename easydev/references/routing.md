# 风险分流与路径切换

主代理在最小调查后选择 quick / normal / full；子代理只回报新证据。先确认交付类型：仅设计、计划、定位、审查、审计或探针不自动扩大为实现。用户明确指定的范围和授权优先。

## 判定依据

读目标、直接调用方、相关测试及实际发布/数据边界。针对与改动有关的风险，区分：

- **已排除**：给出能推翻风险假设的证据，例如所有调用方一起发布、接口输入输出保持不变、修改不改变鉴权决策。仅搜索无命中不能排除动态调用或外部客户端。
- **已确认涉及**：指出受影响入口、不变量和具体失败方式。
- **尚未核实**：已有具体影响线索，但某个决定风险的条件仍不明；继续最小调查，仍不明则进入 full。不能把“还没看”写成“已排除”，也不要求穷尽无依据的假想风险。

简单 quick 的依据可是一句话，不必逐项写排除清单。第二视角信号按事实判定，命中任一条即具备：①改动行为没有现成检查能拦截回归（「现成」指改动前已存在且仍有效的检查，作者本次新增的测试不算；仅新增此前不存在的行为、或纯展示文案与注释改动，不因此命中本条，但期望值仍须追溯到需求或独立契约并写出位置，只写「按实现行为」的按命中本条处理）；②同一改动被两个及以上独立调用方或消费方依赖；③改动共享契约（接口、配置格式或数据语义）且存在本次未改动的使用方；④用户明确要求独立审查。纯私有函数内改动且改动前已有能拦截回归的检查走 quick。

| 路径 | 判定 | 完成方式 |
| --- | --- | --- |
| quick | 目标明确、局部低风险、行为与验证简单；兼容的内部机械重命名也适用 | 按入口核心实施、验证、自查 |
| normal | 调用链与影响有界，具可观察的第二视角信号，没有 full 条件 | 实施、验证、一次独立定向审查与至多一次局部 P2 复审 |
| full | 触及下述高风险边界；重大外部契约或持久数据影响；有具体线索的广泛影响/关键实现不确定性经调查仍未解决；或用户明确要求完整闭环 | 按 orchestration 编排，命中 design 门控才启用独立设计 |

文件数、调用方数量或单纯提到 API 不构成 full 条件。先分流，再判断 full 内的设计门控；不能用设计门控反向把 normal/quick 全部升级。重大契约/数据影响包括破坏兼容、独立发布客户端需迁移、改变存量数据语义或难以回滚；有证据的兼容增量可为 normal，高风险增量仍为 full。

## 高风险边界

以下是典型触发条件，不是关键词匹配或穷尽清单：

| 边界 | 需要核对的实际影响 |
| --- | --- |
| 安全、鉴权与授权 | 信任边界、身份/对象/租户权限、注入与隔离 |
| 支付、敏感数据 | 资金与账务不变量、凭证和个人数据的访问/存储/传输 |
| 并发与数据操作 | 重复执行、一致性、破坏性写入、迁移兼容及失败恢复 |
| 密码学与随机数 | 加密/签名/密钥管理、安全令牌的随机性；普通展示随机数不因此升级 |
| CI、构建、IaC、权限配置 | 凭证暴露、发布/部署权限、制品可信性、基础设施破坏；改注释不因此升级 |
| 依赖与供应链 | 来源/完整性、生命周期脚本、执行权限、生产关键依赖的行为或兼容变化；能证明无相关影响的升级按实际范围分流 |
| 生产日志与遥测 | 密钥、令牌、个人数据是否被记录、外发或扩大可见范围 |

上表按实际影响判定：只改注释、展示文案、错误提示措辞或不含敏感字段的日志措辞、未改变该行所列影响的，不因此进入 full；若因其他理由已在 full，仍按 full 施工与独立审查执行。

## normal 流程

1. 在当前上下文保留目标、基线、影响依据、同一问题尝试数和审查是否已用；不强制创建账本或设计文档。
2. 实施与验证沿用 quick 核心；专项问题按需读 execution 等模块。
3. 真正分派前读取 [模型配置](models.md)。不同实例按 [reviewer-role](reviewer-role.md) 审查完整任务 diff、直接调用方、相关测试和验收；交接原始要求及证据路径，不只给作者结论，不强制加载 full 编排。首轮仅报局部 P2（判定条件见下方「局部 P2 判定」）时，允许一次局部修复并由 reviewer 定向复审，normal 内独立审查至多 2 次；无法确证局部性一律按非局部处理。
4. 无必关项（或局部 P2 经复审关闭）、验收满足且证据对应最终版本时交付，注明“一次独立定向审查”；不称 full 闭环。不影响验收的 P3 列为未实施建议。
5. 确认 P0/P1、非局部范围内 P2、任何验收缺口，或有具体线索的潜在 P0/P1 尚未排除时转 full，继承发现、尝试和已用审查：首轮后转 full 记 `r=1/5`，只余四轮；局部 P2 修复后复审仍报缺陷或现新缺陷时转 full 记 `r=2/5`，只余三轮。若此前用过 full 则在原已用轮次上累加，不能重置为 1。再判断设计门控，必要时先停写补设计审查。禁止通过反复 normal 审查形成无上限修复循环（独立审查硬上限 2 次）。

**局部 P2 判定**（normal 第 3 条局部修复分支的前置，须在报告里逐条对照，不看缺陷措辞）：①不触公共契约：对外 API、CLI 参数与输出、配置格式、事件 schema 均不变；②不改数据或状态语义：表结构、存储格式、既有数据语义、跨请求或跨实例状态不受影响；③不引入新依赖，且不越出本任务已改文件与其直接调用方；④不是验收缺口，也没有带具体线索、尚未排除的潜在 P0/P1；⑤以上任一条无法用 diff、调用方清单或检查结果确证时，一律按非局部处理（转 full）。

没有独立能力或调用受阻时按 [能力降级与审查包](setup.md#能力降级与审查包) 处理，不把自查算作独立审查。审查后发生实质修改，原审查不能直接证明最终版本通过；除首轮仅含局部 P2 且在 normal 内完成一次局部修复及定向复审外，其余实质修改或复审后仍有实质修改一律转 full 复核，纯报告排版修正不计。

## 升级与降级

风险或实际影响扩大时携证据升级，不因单次失败、跨文件或增加一次工具调用升级。仅为刷新预算切路径无效。

允许 full → normal/quick、normal → quick，但同时满足：

- 新证据证明原触发条件不成立，目标路径全部条件满足；写明原假设、反证和剩余验证。
- 用户没有明确要求原档位；没有未关闭的必关项、高影响待验证风险或作者争议。
- 已有独立审查发现若参与降级依据，先完成其关闭确认；不得靠降级绕过设计施工闸、失败审查或预算到顶。

降级只减少尚未发生的流程。已有设计、发现、尝试和审核轮数保留；重入 full 不退还 `d/3`、`r/5`，也不重新获得 normal 审查（已发生的至多 2 次审查不退还、不重置）。先前审查仅在覆盖当前完整变更且证据仍有效时复用。full 降级后已有账本保留，不要求删除。

**能力降级不等于流程降级**：缺少子代理不会把支付、鉴权等任务变成低风险；保留原风险判断，明确缺少的保障。

## 尝试预算

同一问题在整个任务最多三次有新证据的候选修复尝试，quick、normal、full、换实例和模型阶段共用；三次仍失败或证据不足就停止自动修复。纯调查与环境故障不计，但不清除已有记录。问题身份按根因/症状识别，不靠换编号获得新预算。

进入 full 时记录原次数，并应用模型阶段的更严格限制；有 upgrades 时每阶段至多一次，仍受任务总计三次约束。审核轮数是另一预算，不代表额外修复机会。小任务上下文记录足够；需恢复或进入 full 时才转入账本。

## 计量

适用所有档位，不只是 normal；quick 无子代理时只写 `main`。单行格式：`计量：模块=<读取的 references 文件名，按角色分段>；审查=<N>；d=<x>/3；r=<y>/5`；未读记 `无`，未进 full 记 0，未知写原因。`模块` 按角色分段写实际读取的 references 文件名（区别于门控的「模块」=具名包/服务；`main:…；dev:…；reviewer:…`，未参与或未读的角色写 `无`）；子代理自己加载的也计入，宿主能提供读取事件时以读取事件为准，模型自述只作兜底。
