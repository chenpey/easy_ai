# 工作区隔离与分支收尾

仅在任务需要隔离、用户要求或长任务需要独立工作区时使用；局部小改动直接在当前工作区完成，不必建工作树。同一任务仍只有单一写入者。

## 创建隔离工作区

- 优先宿主原生工具（如 Codex 的工作树创建/归档工具）；已有原生工具时不手工执行 `git worktree add`，避免宿主看不到的幽灵状态。
- 无原生工具时回退 `git worktree add`；先确认已在隔离工作区或处于子模块（子模块不是 worktree），不重复创建。目标目录优先项目已有的 `.worktrees/` 约定，创建前确认其被 `.gitignore` 忽略。
- 基准按任务指定分支或宿主默认分支；不静默从 main/master 开始，除非用户明确同意。
- 创建前检查当前工作区。有未提交、未跟踪或影响任务的忽略文件时，明确采用“从基准分支全新开始”或“迁移当前完整状态”之一；选择迁移须先按 [baseline-safety.md](baseline-safety.md)保护并记录原状态，迁移全部已跟踪及影响任务的未跟踪/忽略文件与恢复路径，不静默丢弃或只复制部分文件。
- 创建失败（权限/沙箱）时不绕过限制；默认停止隔离工作及依赖它的写入，说明原因。只有用户明确同意降级或在当前目录继续时才继续，并记录基线、原计划隔离缺口与采用的替代方案。
- 新工作区先运行项目相关检查建立干净基线；失败时报告，不让脏基线污染后续结论。

## 收尾与集成

1. 先完整跑本任务的验证（测试、lint、构建按项目实际情况），绿了再进入集成；失败则报告并停止。
2. 检测当前是普通仓库、命名分支工作树还是外部管理的 detached HEAD，据此选择选项；确认要合入的基准分支，不硬编码 main/master。
3. 先核对授权基线：集成方式与目标分支已获用户明确授权时按授权执行；未获授权时呈现并等待用户选择：本地合并 / 推送并创建 PR / 保留现状，detached HEAD 只有后两项。推送、创建 PR 与发布始终需要用户明确授权并遵守宿主规则；集成决定属于用户，不代为决定。
4. 本地集成本任务时，优先在独立集成分支或工作树完成合并并验证，再以快进或明确的合并提交更新目标分支；直接在目标分支合并时，先确认没有未保护改动并记录集成前提交。合并后重跑验证，失败时停止推送、发布与清理，保留候选分支、工作树和恢复引用，先让用户选择安全回退；不得覆盖集成期间出现的新改动。推送、创建 PR、发布按宿主规则与实际授权执行。
5. 清理仅针对本任务创建且已确认不再需要的部分：优先宿主原生清理工具，回退 `git worktree remove <本任务的工作树路径>`；不附带仓库级 `git worktree prune`，它也会删除仓库中其他工作目录暂不可达的工作树元数据。删除被拒绝时列出未提交内容让用户选择，绝不擅自 `--force` 或丢弃分支。

## 边界

- 只记录本次隔离与集成状态，不复制凭证或无关文件；工作树与分支的删除属于不可逆操作，必须等用户明确选择。
- 无法使用隔离工作区时如实说明，仍按 [baseline-safety.md](baseline-safety.md) 的任务基线保护用户已有内容。
